# طراحی قابلیت «ثبت دارو» — بخشی از پرونده سلامت بیمار

**نسخه سند:** 1.0 (فقط طراحی — پیاده‌سازی منوط به تأیید مالک پروژه)
**شاخه:** `docs/medication-log-design` | **تاریخ:** 2026-11-09
**دامنه جغرافیایی:** فقط شیراز | **وضعیت:** منتظر تأیید — **هیچ کدی پیاده‌سازی نشده است**

---

## ۱. هدف و جایگاه

قابلیت «ثبت دارو» به بیمار اجازه می‌دهد روند مصرف داروهای خود را **ثبت، پیگیری و مرور** کند؛ به‌عنوان بخشی از «پرونده سلامت» شخصی او در نوبتیار.

**چه هست:** دفترچهٔ شخصی دارو (نام، دوز، زمان، مدت، پزشک، وضعیت) + تاریخچهٔ تغییرات.
**چه نیست (مرزهای صریح):**

- ❌ **نسخه الکترونیک نیست** و به‌هیچ‌عنوان معرفی/بازاریابی نمی‌شود.
- ❌ **هیچ توصیهٔ پزشکی** نمی‌دهد؛ هیچ پیام «بهتر است دوز را کم/زیاد کنید» تولید نمی‌شود.
- ❌ **هیچ تغییری خودکار در دوز/برنامهٔ مصرف** انجام نمی‌دهد — هر تغییر فقط با ورودی خود بیمار ثبت می‌شود.
- ❌ ادغام با سامانه نسخ الکترونیک کشور ندارد (خارج از دامنهٔ این مرحله).

## ۲. رابطه با قابلیت‌های موجود (اصل «عدم بازسازی»)

در نوبتیار **یادآور دارو** از قبل وجود دارد (`models.MedicationReminder` + `meds.py`): فقط نام دارو + ساعت‌های یادآوری، در ربات بله.

| جنبه | یادآور دارو (موجود) | ثبت دارو (این طراحی) |
|---|---|---|
| کارکرد | یادآوری زمانی | پروندهٔ دارویی با جزئیات کامل |
| داده | نام (۶۰ کاراکتر) + ساعت | دوز، واحد، مدت، علت، پزشک، وضعیت، تاریخچه |
| وضعیت | فعال/متوقف | فعال / تکمیل‌شده / متوقف‌شده |
| سطح دسترسی | ربات (chat_id) | ربات در فاز ۱ + وب در فاز ۲ |

**تصمیم طراحی:** این دو ادغام نمی‌شوند و یکی حذف نمی‌شود؛ «ثبت دارو» لایهٔ کامل‌ترِ همان پرونده است. در فاز ۲ دکمهٔ «یادآوری» در کارت دارو، یادآور موجود را پیش‌پر می‌کند (بدون تکرار ساختار).

## ۳. مدل داده (پیشنهاد — مهاجرت افزایشی 0007)

> **یادداشت شمارهٔ مهاجرت (بازبینی نهایی 2026-11-09):** شمارهٔ `0007` به این فرض وابسته است که شاخهٔ «همراه بیمار» (`feat/patient-companion-v0.10.0` با مهاجرت `0006_patient_companion`) پیش از پیاده‌سازی این قابلیت ادغام شود. در صورت تغییر ترتیب ادغام، شمارهٔ مهاجرت باید «بزرگ‌ترین شمارهٔ موجود + ۱» شود تا از تداخل جلوگیری گردد.

```
patient_medications
───────────────────
id               PK
chat_id          VARCHAR(50)  NOT NULL, INDEX   -- هویت بیمار در بله (فاز ۱)
name             VARCHAR(120) NOT NULL           -- نام دارو
dose_amount      VARCHAR(20)  NULL               -- مقدار دوز («۱»، «2.5»)
dose_unit        VARCHAR(20)  NULL               -- قرص/کپسول/شربت/قطره/آمپول/اسپری/بیمارستانی
frequency_kind   VARCHAR(20)  NOT NULL DEFAULT 'daily'   -- daily | interval | weekly
frequency_value  VARCHAR(120) NULL               -- «صبح و شب» یا «هر ۸ ساعت» (متن آزاد کنترل‌شده)
times_of_day     VARCHAR(200) NULL               -- «08:00,20:00» (پیش‌پرکنندهٔ یادآور)
start_date       DATE         NOT NULL           -- تاریخ شروع (شمسی در UI، میلادی در DB)
end_date         DATE         NULL               -- NULL = بدون تاریخ پایان مشخص
duration_days    INTEGER      NULL               -- یا مدت مصرف
reason           VARCHAR(200) NULL               -- علت مصرف (اختیاری)
prescriber       VARCHAR(120) NULL               -- نام پزشک تجویزکننده (اختیاری)
notes            VARCHAR(500) NULL               -- توضیحات تکمیلی
status           VARCHAR(12)  NOT NULL DEFAULT 'active'   -- active | completed | stopped
status_changed_at DATETIME    NULL
created_at / updated_at DATETIME DEFAULT utcnow

medication_change_logs
──────────────────────
id               PK
medication_id    FK → patient_medications.id ON DELETE CASCADE
field            VARCHAR(30)                    -- نام فیلد تغییر‌یافته یا 'status'
old_value        VARCHAR(255) NULL
new_value        VARCHAR(255) NULL
changed_at       DATETIME DEFAULT utcnow
```

اصول:

- **حذف نرم نیست؛ دو وضعیت پایان داریم:** «تکمیل‌شده» (دوره تمام شد) و «متوقف‌شده» (پیش از پایان). رکورد حذف فیزیکی نمی‌شود تا سابقه محفوظ بماند؛ حذف فیزیکی فقط با درخواست صریح بیمار (حق فراموشی — الگوی «همراه بیمار»).
- تاریخچه فقط «چه فیلدی، از چه مقداری به چه مقداری» است — بدون هیچ متن پنهان‌شدهٔ اضافی.
- سقف: **۵۰ دارو در هر بیمار** (ضد سوءاستفاده؛ یادآور فعلی ۱۰ یادآور فعال دارد و دست‌نخورده می‌ماند).
- **هیچ فیلد دارویی در لاگ‌ها نوشته نمی‌شود** (دادهٔ سلامتی — الگوی فعلی meds.py).

## ۴. طراحی API (فاز ۱ — از طریق ربات؛ فاز ۲ — وب)

همه اندپوینت‌ها با هویت ربات (chat_id مشتق‌شده از گفتگو — **هرگز از ورودی کاربر**) و در فاز وب با احراز هویت واقعی:

| عملیات | اندپوینت (پیشنهادی) | نکته امنیتی |
|---|---|---|
| ثبت داروی جدید | `POST /api/medications` | سقف ۵۰، اعتبارسنجی سخت |
| داروهای فعال | `GET /api/medications?status=active` | فیلتر اجباری `chat_id` |
| سوابق (تکمیل/متوقف) | `GET /api/medications?status=completed,stopped` | فیلتر اجباری `chat_id` |
| ویرایش | `PATCH /api/medications/{id}` | **همیشه** `WHERE chat_id = …` (ضد IDOR) |
| ثبت پایان/توقف | `POST /api/medications/{id}/finish` یا `/stop` | ثبت در change_logs |
| تاریخچه تغییرات | `GET /api/medications/{id}/history` | فقط مالک |

**ضد IDOR (الگوی مأموریت «همراه بیمار»):** هر کوئری همیشه هم `id` و هم `chat_id` را فیلتر می‌کند؛ پاسخ 404 برای «موجود ولی مال شما نیست» (بدون افشای وجود).

**اعتبارسنجی ورودی:** نام ۲–۱۲۰ نویسه؛ دوز فقط ارقام/نقطه (نرمال‌سازی ارقام فارسی — fa_utils)؛ واحد از فهرست ثابت؛ تاریخ معتبر؛ متن‌ها سقف‌دار. هیچ فیلدی آزادِ بی‌سقف نیست.

## ۵. تجربه کاربری (ربات بله — فاز ۱)

ورودی منوی اصلی (پیشنهاد — جای دقیق با تأیید مالک): دکمهٔ «💊 پرونده دارویی من» کنار «⏰ یادآوری دارو».

جریان‌ها (هر مرحله با «انصراف» و «بازگشت به منو» — الگوی فعلی ربات):

1. **ثبت دارو:** نام → دوز+واحد (دکمه‌های واحد) → زمان/تعداد دفعات (الگوی پارسر ساعت meds: «۸ صبح و ۹ شب») → شروع + مدت/پایان (اختیاری) → علت (اختیاری) → پزشک (اختیاری) → تأیید خلاصه → ثبت.
2. **داروهای فعال:** کارت خلاصه هر دارو (نام، دوز، ساعت‌ها، روزهای باقیمانده) + دکمه‌های «ویرایش / پایان دوره / توقف».
3. **سوابق:** فهرست خواندنیِ تکمیل‌شده‌ها و متوقف‌شده‌ها با تاریخ پایان.
4. **ویرایش:** انتخاب فیلد → مقدار جدید → ثبت + نوشتن خودکار در تاریخچه.
5. **پایان/توقف:** سؤال تأیید + انتخاب علت اختیاری → ثبت وضعیت (بدون حذف).
6. **تاریخچه:** خط زمانی «چه تغییر کرد و کِی».

**هشدارهای ثابت (الزامی در همه UI):** «این دفترچه فقط ثبت شخصی است و توصیهٔ پزشکی نیست؛ برای تغییر دارو با پزشک خود مشورت کنید.» — در شروع، در تأیید نهایی و در کارت هر دارو (قابل جمع‌شدن).

## ۶. امنیت و حریم خصوصی

- دادهٔ دارویی = **دادهٔ سلامتی محرمانه**: فقط خود بیمار (chat_id) به دادهٔ خودش می‌رسد؛ هیچ مسیر عمومی/ادمینی برای دیدن محتوای دارویی بیماران وجود نخواهد داشت (ادمین فقط شمارش‌های بی‌نام می‌بیند، در صورت نیاز آینده).
- **لاگ‌گیری:** هیچ نام دارو/دوز/علتی در لاگ نمی‌نشیند (الگوی فعلی meds.py: «هیچ داده دارویی در لاگ نوشته نمی‌شود»).
- **بکاپ:** خروجی `/api/admin/backup` فعلاً این جداول را شامل **نمی‌شود** (تصمیم: تا تصمیم مالک دربارهٔ پوشش دادهٔ سلامتی در بکاپ ادمین، خارج می‌ماند — ریسک افشای گروهی کمتر شود).
- رمزنگاری در ترانزیت: HTTPS لیارا (موجود). رمزنگاری at-rest ستونی در فاز فعلی لازم دیده نشد (دیتابیس در شبکهٔ خصوصی لیارا است) — به‌عنوان آیتم «تصمیم مالک» ثبت شده است.
- **پاک‌سازی:** درخواست حذف کامل پرونده دارویی بیمار = حذف فیزیکی کسکید (حق فراموشی).

## ۷. برنامهٔ پیاده‌سازی پیشنهادی (پس از تأیید)

| مرحله | محتوا | برآورد |
|---|---|---|
| 1 | مهاجرت 0007 (دو جدول، افزایشی، idempotent) + مدل‌ها | ~۲ ساعت |
| 2 | سرویس `med_log_svc.py` (CRUD + تاریخچه + سقف‌ها) + تست‌های واحد | ~۳ ساعت |
| 3 | اندپوینت‌های API با فیلتر اجباری chat_id + تست‌های ضد IDOR | ~۲ ساعت |
| 4 | ربات: منو، FSM ثبت/ویرایش/پایان، کارت‌ها + تست‌های سناریو | ~۴ ساعت |
| 5 | رگرسیون کامل + مستندسازی | ~۱ ساعت |

ریسک‌ها: حجم FSM ربات (به‌اندازهٔ «همراه بیمار» کنترل‌شده)، اشتباه کاربر در تاریخ‌ها (کالیبره با تقویم شمسی موجود)، توقّع یادآوری خودکارِ روی داروهای ثبت‌شده (فاز ۲ — اعلام صادقانه که فعلاً یادآوری فقط از بخش «یادآور دارو» است).

## ۸. سؤالات باز — نیازمند تصمیم مالک

1. جای دکمه در منوی اصلی ربات و متن دقیق آن؟ («💊 پرونده دارویی من» پیشنهاد است)
2. آیا فاز وب (پرونده در سایت) هم اکنون طراحی شود یا فقط ربات؟
3. آیا «یادآوری» داروهای ثبت‌شده باید خودکار شود (اتصال به یادآور موجود) یا دستی بماند؟
4. پوشش دادهٔ دارویی در بکاپ ادمین: بله/خیر/با رمز جداگانه؟
5. آیا ثبت «کد ملی» در پرونده دارویی لازم است (اتصال آینده به نوبت‌ها) یا chat_id کافی است؟
